## 1. 项目定位与目标

一个挂靠在 lzhdev.com 下的 utilities webapp，三重定位：

1. **自用** — 日常顺手的小工具集合
2. **家人使用** — 需要轻量鉴权，但绝不引入重型账号体系
3. **开源产品** — 代码公开、文档完整、任何人可自部署

功能方向（初期，会持续演进）：

| 方向 | 说明 |
|------|------|
| AI tools | 前端工具通过后端代理调用 AI API；API key 只存服务端 |
| Skills 加载 | 初期预留动态资源能力；读书助手后来采用受限书籍工具与固定来源版本，具体边界见 ARCHITECTURE §3–6 |
| 动态 API | AI 之外的服务端接口：数据持久化、文件处理等 |
| 纯前端小工具 | 计算器、格式化、转换器等，无需后端 |

站点地址：**https://utils.lzhdev.com**

**核心目的（2026-10-04 明确）**：引入 Docker 与自建服务器的根本原因，是要在后台服务器上运行 **Claude Code 这类 AI agent**；utils webapp 本质是套在 agent 外面的 **UI 壳**——用户在浏览器里直接与服务器上的 agent 对话。其余工具（AI 代理、纯前端小工具）围绕这一核心展开。对 M4 架构的含义：① agent 会话管理（Claude Code Agent SDK / 进程级管理，运行在应用容器内或独立 sidecar 容器）；② SSE/流式输出；③ 会话持久化（SQLite on volume）；④ 家人鉴权前置到 agent 会话之上。

## 3. 域名与路由方案

以下保留原方案与 M2 决策的演进顺序；实际拓扑和 SSH 操作以 DEPLOYMENT 为准。

### 决策：`utils.lzhdev.com` 子域名 ✅

**否决 lzhdev.com/utils path 方案的原因**：主站在 Cloudflare Pages 上，Pages 无法直接把任意 path 反向代理到外部源站；path 方案必须额外加一个 Cloudflare Worker 做代理，引入新故障点和维护成本。子域名方案完全绕开这一层。

**架构**：

```
用户 → Cloudflare（proxied DNS，TLS 终结/CDN/WAF）
     → 源站服务器 Caddy/nginx 反代（80/443）
     → utils 容器（内网端口，如 127.0.0.1:3100）
```

**配置要点**：

- Cloudflare DNS 添加 A 记录 `utils` → 服务器 IP，开启 proxied（橙色云）
- Cloudflare SSL/TLS 模式设为 **Full (strict)**；源站证书用 Cloudflare Origin CA（15 年免续期）或 Caddy DNS-01 challenge（需 CF API token）
- 附带收益：Next.js **不需要 basePath**，避开子路径部署的整类坑（资源 404、stale chunk、cookie path 等，调研见 §9）
- 可选加固：**Cloudflare Tunnel**（cloudflared）——服务器不开任何入站端口，SSH 部署亦可走隧道；适合家庭/小 VPS 场景
- 可在 Cloudflare Pages 项目加 `_redirects`：`/utils https://utils.lzhdev.com 301`，保留原 URL 记忆点（GH Pages 源同步加）

### 3.1 M2 实施拓扑（2026-10-04 定稿，三项决策已确认）

**服务器**：GCP `instance-20260904-233454`（e2-micro · 1GB RAM · Debian 13.7 · us-east1-c · 外网 IP 35.229.94.124 · GCP 永久免费层）。当前无 Docker，需安装 + 加 swap 兜底。

**入站流量（决策 1）：Cloudflare Tunnel + IAP SSH —— 服务器不开任何入站端口**

```
浏览器 → utils.lzhdev.com（CF 边缘 TLS）
       → Cloudflare Tunnel（cloudflared 出站连接 CF 边缘）
       → VM localhost:3100（utils 容器）
SSH 管理/部署：gcloud compute ssh --tunnel-through-iap（IAP 网段 35.235.240.0/20）
```

配套变更：防火墙 22 端口从 0.0.0.0/0 收紧到 35.235.240.0/20（IAP 专用网段）；443 规则不用（无入站 TLS 需求）。

**CI/CD 认证（决策 2）：Workload Identity Federation 无密钥**

- WIF pool/provider 绑定 `sileneer/utils` 仓库 + main 分支条件；专用 Service Account（如 `utils-deploy@…`）
- 最小角色：`roles/iap.tunnelResourceAccessor` + `roles/compute.osAdminLogin`（ExternalAccount 变体，部署脚本需要 sudo 跑 docker）+ `roles/iam.serviceAccountUser`
- Actions 侧：`google-github-actions/auth@v2`（OIDC，零长期密钥）+ `google-github-actions/ssh-compute` 或 `gcloud compute ssh --tunnel-through-iap`
- 显式否决：SA JSON 密钥 / SSH 私钥存 GitHub Secrets（长期泄露面）

**引导顺序（M2/M3 交织）**：服务器要拉镜像 → 镜像必须先存在于 GHCR → 所以先落地 CI 的 build+push 阶段（M3 前半），再装 Docker + compose pull 起服务，最后接 Cloudflare Tunnel 与 DNS。

**用户侧待提供**：~~Cloudflare API Token~~ ✅ 已完成（2026-10-04，agent 经浏览器在 dashboard 创建 `utils-deploy` token：Account→Cloudflare Tunnel:Edit + Zone lzhdev.com→DNS:Edit，验证 active）。Token 与 account/zone ID 存于项目根 `.env.cloudflare`（被 `.gitignore` 的 `.env.*` 规则覆盖，绝不入库）。其余（WIF、VM 系统级操作）由 agent 通过本机 gcloud/SSH 完成。

## 4. 部署架构：原方案评审与最终设计

### 4.1 原方案评审

原流程：`push main → GitHub Actions → HTTP 请求通知服务器 → 服务器同步 repo → 服务器自制 Docker 重建部署`。方向正确（事件驱动替代定时同步 ✅），但有以下问题：

| # | 问题 | 修正 |
|---|------|------|
| 1 | **在服务器上构建镜像**：Next.js 构建内存峰值可达 1–2GB，小 VPS 有 OOM 风险；部署慢、构建期间与线上服务抢资源 | 构建放在 GitHub Actions，镜像推到 GHCR；服务器只做 `docker compose pull && up -d` |
| 2 | **服务器同步 repo 需要 Git 凭证**（deploy key / PAT），扩大泄露面 | 镜像方案下服务器**不需要任何 GitHub 凭证**（GHCR 公共镜像匿名拉取）；compose 文件由部署步骤从 Actions 直接 scp 上传 |
| 3 | **公开的部署触发端点**若不验证身份，任何人都能触发重建（DoS 向量） | 部署通道二选一（见 4.2）：A) Actions SSH 直连；B) 服务器上 webhook receiver（Bearer token + flock） |
| 4 | **部署失败不可见**："发个请求就完事"，Actions 无感知成败 | SSH 方案的 exit code 直接传播回 Actions 日志；另加 `/api/health` 健康检查 + healthchecks.io 死信开关 |
| 5 | **并发竞争**：连续 push 触发并行重建，互相踩踏 | Actions `concurrency: deploy-prod` 串行化 + 服务器端 `flock` 双保险 |
| 6 | **无回滚设计**：重建部署下回滚 = revert + 重新全量部署 | 镜像按 git SHA 打 tag 并保留最近若干个；回滚 = compose 指回旧 tag 一条命令 |

### 4.2 已采用的设计与被替代草案

选择 CI 构建镜像、服务器拉取运行，避免小 VM 上构建导致 OOM；按提交标记镜像，
串行部署、健康门禁及回滚提供可核对的发布结果。实际流水线只记录在 DEPLOYMENT §2–3。

原草案的 alpine runner、长期 SSH key/GitHub Secrets、webhook、80/443 入站反代和
共享口令/middleware 均不作为现行方案：后续分别改用 SDK 兼容的 slim 镜像、
WIF + 临时 SSH key/IAP、Cloudflare Tunnel 及 Better Auth/SQLite 账号。
共享口令由公开邮箱账号替代（§11），再提升为全站账号系统（§13）。
Secrets 只在服务端运行时注入，镜像和浏览器不能包含私有配置。

数据库和书籍状态放持久卷，账号/会话归属、版本与备份不可因镜像回滚被替换或清理。
数据契约见 ARCHITECTURE §4–6；监控、部署锁、镜像保留和恢复演练见 DEPLOYMENT。

### 4.3 补充：为什么不用轮询式自动更新

containrrr/watchtower 原版已停止维护且存在 Docker 29+ 兼容问题；社区维护 fork 为 [nicholas-fedor/watchtower](https://github.com/nicholas-fedor/watchtower)，另有 What's Up Docker (WUD)、Diun 等替代。轮询方案延迟不可控且不利于生产，本项目不采用，仅作备选记录。

## 5. 技术选型

### 决策：Next.js（App Router + TypeScript，standalone 输出）✅

**依据**：

- **需求匹配**：Route Handlers 做 AI 代理与动态 API；Server Components 减少前端样板。早期 middleware 鉴权草案后来由服务端账号/资源归属验证替代（ARCHITECTURE §5）。
- **自托管一等公民**：`output: 'standalone'` 官方支持，镜像可控；basePath/rewrites 原生（子域名方案下暂用不上，保留灵活性）
- **开源协作友好**：生态最大、贡献者上手成本最低、AI 编码工具对 Next.js 先验最强
- **备选对比**：
  - *Hono + Vite + React*：更轻（镜像 ~60MB、内存更小）、2025 增速最快，但项目结构/鉴权等规范需自搭，开源模板性弱
  - *SvelteKit*：DX 口碑好、产物小，但生态较小、子路径支持有边缘问题、贡献者池小

版本基线：Node 22+（本地 24）；Next.js 以 M1 时 `create-next-app@latest` 的稳定版为准。

**UI 技术栈（2026-10-04 敲定）**：Tailwind CSS v4 + shadcn/ui + lucide-react + next-themes + sonner + react-hook-form/zod。完整设计规范（设计 token、组件规则、布局模式、无障碍、防反复调整条款）见 [DESIGN.md](DESIGN.md)，状态为 **BINDING**，所有 UI 开发必须遵循。

**i18n（2026-10-05 落地）**：utils 站点双语——英文（默认回退）+ 简体中文，next-intl cookie 模式（无 URL 前缀）；默认跟随访客系统语言（Accept-Language），页头语言切换器写 `NEXT_LOCALE` cookie 覆盖。所有可见文案集中在 `messages/{en,zh}.json`。仅 utils 站点配置，不涉及主站。页脚版权行按所有者要求移除。

## 8. 风险与未决问题

- **小 VM 容量**：构建已移到 CI；单并发、内存和保留来源版本的磁盘需求仍需观测。
  较高日配额不能证明吞吐量足够，不能擅自清理来源或备份以释放磁盘。
- **AI 质量与调用成本**：受限书籍工具、用户/全站 turn 上限与真实用量展示已实现；
  turn 上限不是货币预算，定位有效不代表回答忠实。实际剩余验收与续答超时见 HANDOVER/GOTCHAS。
- **实机与备份验收**：浏览器模拟不能替代手机键盘/IME；异地备份须先明确归属、费用、
  保留和恢复方案。当前待配合项只列在 HANDOVER，操作方案只放 DEPLOYMENT。
- **主站与 utils 的边界**：主站静态托管与本仓库的容器应用是不同项目；不要把主站
  的分支、模板或路由迁移当作 utils 的实现事实。
- **公开仓库纪律**：秘密永不入库；测试使用运行时生成的临时凭证，误报示例不能当作真实泄密，
  也不能未经核查把告警直接忽略。具体排查教训见 GOTCHAS。

### 10.1 审批范围与交付目标

### 10.2 第一批：会话可靠性与恢复

**实现**

- 将会话状态集中到 ReadingShell 上层的共享控制器/hook，桌面面板与移动 Sheet
  使用同一消息、草稿、模型、请求和会话状态。开关面板、切换宽度不重复发请求。
- 为消息/回合/请求建立稳定 ID；明确提交中、生成中、完成、失败和已停止状态。
  正常结束只结算一次；服务端失败不再随后发送成功结束。解析器处理分块 UTF-8、
  keepalive 和没有终止事件的 EOF，保留未完成内容并明确标记。
- “停止”取消客户端请求并传递到 Agent；“新对话”先取消/失效旧请求，再切换
  会话。即使旧请求的最后数据稍后到达，也不能写入新对话。
- 失败消息提供手动重试，保留问题并复用失败回合的位置；忙碌/限流不自动重试。
  生成中可编辑下一条草稿，发送仍按现有单请求限制执行。
- 增加受现有鉴权保护的历史读取能力，仅读取当前 UUID 对应的会话，不增加全量
  会话枚举。兼容旧 JSON；旧消息补稳定 ID/默认状态，写入采用临时文件原子替换。
- 已完成与失败/停止的回合分别保存；失败回合不能作为正常答案恢复。恢复历史时
  校准 SDK 上下文：对失败/中断后上下文不确定的 SDK 会话，使用已完成对话重建
  上下文，再重试当前问题，避免隐藏的失败回合重复进入模型。
- 保留刷新前的输入草稿；普通刷新恢复已保存消息。生成中整页刷新按中断处理，
  不承诺断线续流。处理存储不可用、401/口令过期及历史加载失败。

**验收**

1. 正常流、完整消息回退和多段数据均只显示一份答案。
2. 在等待首字、生成中和终止边界停止/新建对话，均不串话；后端释放占用。
3. 空 EOF、部分 EOF、超时、429、401、Agent 错误均有明确状态和可行恢复操作。
4. 手机关闭重开、桌面/手机切换、普通刷新后，历史和草稿按约定恢复。
5. 重试不重复添加问题；后续追问使用的上下文与用户可见的完成历史一致。
6. 旧会话文件可读；无鉴权请求被拒绝；非法 UUID 无法读取文件。

**验收**：中文输入法不误发；多行输入与复制正确；流式 Markdown 可读；长答案

### 10.4 第三批：原文与聊天联动

**先统一来源版本**

- 识别发布 HTML 声明的正文提交，建立版本清单；查书目录取同一提交的原文。
  HTML 与原文作为一套版本准备完毕后再切换当前版本，刷新失败保留上一套。
- 聊天请求绑定读者当前看到的书籍版本；已有 SDK 会话继续绑定其原版本。
  版本变化时明确提示新开对话使用新版，避免旧上下文静默混入新版来源。
- HTML 缺少可验证修订标识或对应提交拉取失败时，不能宣称已同步；优先保留
  上一套验证版本。首次准备无可用版本则报告具体阻塞，不自行改用未经确认的来源。

**再加入联动**

- 在本项目的书籍代理中注入轻量桥接脚本，不修改上游书籍仓库。
  消息验证同源、具体 iframe 来源与数据格式，并清理监听器。
- 读者选中文字/条目后出现“问 AI”；问题区显示可移除的原文片段和出处。
  只发送读者明确选择的有限片段与来源标识，不把整个页面随每轮问题发送。
- 把可确定的“第 X 节第 Y 条”引用做成来源入口；确认版本和条目存在后，点击
  让阅读区解除必要筛选、加载目标、滚动并高亮。手机先收起 Sheet 再展示目标，
  再打开聊天时仍保留原消息与草稿。
- 分组、范围和模糊引用只有在可无歧义解析时才生成入口；不存在的引用保留原文
  并说明无法定位，不伪造来源。“已验证”仅指定位/版本一致，不表示论述已被事实核查。

**验收**：选文上下文可见且可移除；连续追问不意外重复附加片段；引用能定位
被筛选/尚未加载的条目；手机能完成“回答 → 原文 → 回到聊天”；来源不存在、
版本更新和刷新失败均有明确退路；Agent 与阅读区的修订号一致且可核验。

### 11.1 现状与选型

现有 `src/lib/agent/auth.ts` 只校验共享口令和签名到期时间，无法返回用户 ID；
`/api/agent/auth` 的 IP 限流存在进程内，重启清零；聊天 JSON 无用户归属。
目前鉴权通过的人可按 UUID 获取同一共享空间的会话。这适合原来的家庭口令，
不能直接沿用为不同公开用户之间的权限模型。

推荐 **Better Auth（自托管）＋ SQLite（现有持久卷）＋ Brevo 事务邮件 API**。

- [Better Auth](https://better-auth.com/docs/integrations/next) 提供 Next.js
  Route Handler 集成；[邮箱密码模块](https://better-auth.com/docs/authentication/email-password)
  管理密码哈希和登录会话；[Email OTP](https://better-auth.com/docs/plugins/email-otp)
  支持邮箱验证和找回密码。其核心库采用
  [MIT](https://github.com/better-auth/better-auth/blob/main/LICENSE.md)，账号数据留在本机。
- [SQLite 适配](https://better-auth.com/docs/adapters/sqlite) 支持 better-sqlite3。
  当前单容器、1 GB VM、单 Agent 请求，适合小规模账号先落地；不额外运行
  PostgreSQL/Redis 或开通托管数据库。未来多实例/高写入需求再评估 PostgreSQL。
- 本轮是调研推荐，不把上述库写成已安装。批准实施后锁定兼容版本并验证
  Windows 开发、Node 22 Debian slim 和 standalone 原生依赖打包。
  Better Auth 的登录模块能满足当前需求，自写整套密码/会话系统的维护成本更高。

### 11.2 发信服务调查

下列是 2026-10-07 查询到的官方公开额度，不代表已通过账号审核或实测送达。
验证码属于事务邮件；不要用营销联系人额度代替事务发信额度。

| 服务 | 免费事务邮件额度 | 主要限制 / 成本取舍 | 本项目判断 |
| --- | --- | --- | --- |
| [Brevo](https://help.brevo.com/hc/en-us/articles/208580669-FAQs-What-are-the-limits-of-the-Free-plan) | 300 封/日，无免费期限；未用额度不结转 | 达上限后事务邮件进入重试队列；免费品牌标记政策需在验证码模板中确认 | 免费额度优先，推荐首选；30 天理论上限 9,000 封是算术换算，不能跨天集中使用 |
| [Mailjet](https://documentation.mailjet.com/hc/en-us/articles/360043048393-What-is-this-200-emails-per-day-limit-on-free-accounts) | 6,000 封/月，200 封/日 | 月限额＋日限额，仍需验证发信身份 | 免费备用候选 |
| [Resend](https://resend.com/pricing) | 3,000 封/月，100 封/日 | [额度规则](https://resend.com/docs/knowledge-base/account-quotas-and-limits) 包含收发；Pro 为 $20/月、50,000 封，无日上限 | Next.js 接入便利；免费突发容量低于前两者，适合作为开发便利优先的替代选择 |
| [Amazon SES](https://aws.amazon.com/ses/pricing/) | 新账号有期限/资格限制的促销额度，不能当长期免费 | 按量基础出站费 $0.10/1,000 封，另计数据/选用功能；[sandbox](https://docs.aws.amazon.com/ses/latest/dg/request-production-access.html) 限制收件人，公开注册须申请生产权限 | 免费额度不足后的低单价增长方案，接入与审核成本更高 |

**推荐理由：** 用户把免费和少限制放在前面；Brevo 在这几个成熟候选中日免费额度
最高。普通密码登录无需邮件，消耗集中在注册、重发、找回密码，当前不需要每次
登录发送 OTP。Brevo 是拟选主服务，Mailjet/Resend 为可替换适配；首版不做多供应商
自动故障切换，避免一个验证码被多个发送流程重复投递。

**选型落地条件：**

1. Owner 创建/登录 Brevo 账号，完成
   [事务平台激活](https://help.brevo.com/hc/en-us/articles/115000188150-Troubleshooting-Issues-with-Brevo-SMTP)
   （官方说明可能需要联系支持）。没有激活不能宣称可用于公开收件人。
2. 使用独立发信子域，例如 `auth.lzhdev.com`，发件人
   `Utils <noreply@auth.lzhdev.com>`；按
   [Brevo 域名认证](https://help.brevo.com/hc/en-us/articles/12163873383186-Authenticate-your-domain-with-Brevo-Brevo-code-DKIM-DMARC)
   提供的记录配置 DNS，保护现有主域邮件记录，不自行重复添加 SPF/DMARC。
   API key 仅服务端 env，HTTPS API 避免新增 SMTP 端口配置。
3. 用 owner 授权的测试邮箱覆盖 Gmail、Outlook、QQ、163，记录延迟、垃圾箱和
   实际模板/品牌标记。任何“稳定送达国内邮箱”的判断须有实测，不能由额度推出。
4. 系统自己做原子发信预算预留、检查服务额度并提前留出找回密码容量；接近
   日限额时拒绝新发送并给出恢复时间，不让 5–10 分钟 OTP 等到第二天。
   API 接受、成功送达和邮箱已验证是三个不同状态；短码过期后必须重新申请。
5. 抽象一个服务端 mail adapter，记录请求/供应商消息 ID 与结果；不存明文 OTP
   或带验证码的邮件正文，不记录密码/密钥。无需为首版再加邮件 SDK/邮件编辑器。

### 11.3 数据库安排

拟使用 `/app/data/utils.sqlite`，宿主机沿用 `/opt/utils/data` 持久挂载；数据库
不进镜像或 Git，书籍 HTML/Markdown 和 SDK 文件仍放文件系统。

| 逻辑表（实施时按锁定框架 schema 生成/映射） | 内容与用途 |
| --- | --- |
| users | 稳定用户 ID、规范化唯一邮箱、昵称、验证状态、server-owned role/status |
| accounts | 用户对应 credential 账号和密码哈希；不另复制密码到 users |
| login_sessions | 数据库登录会话、用户外键、过期时间；支持退出和撤销 |
| verifications | 按邮箱＋用途区分的 OTP 校验记录和过期信息，由认证插件管理 |
| auth_rate_limits | 框架请求计数；补充服务端邮箱/IP/全站限流键，原子检查＋递增 |
| conversations | owner_user_id、原会话 UUID、书籍版本、SDK ID、needsRebuild、时间戳 |
| messages | 对话外键、message/turn ID、角色、正文、context/revision、完成/失败状态 |
| ai_usage | 用户/请求的额度预留、运行结果、可获得的 usage；不把缺失 token 当 0 成本 |
| mail_requests | 脱敏发送元数据、用途、供应商 ID、发送状态与预算预留；无明文短码 |

认证表以 [Better Auth schema](https://better-auth.com/docs/concepts/database) 为准，
不自行设计一套与框架并行的登录 session/验证码存储。server-owned role/status 禁止
客户端注册时赋值；首次公开注册者不能自动成为管理员。Owner 账号验证后通过明确
服务端管理命令提权。邮箱规范化不自行删除 Gmail 的点号或 plus 部分。

拟开启外键、WAL、合理 busy timeout；保持事务短小，不在邮件/API 等待或 SSE
全程中持有数据库事务，消息在阶段/结束时保存，不逐 token 写库。
[WAL](https://www.sqlite.org/wal.html) 适用于本地单机，仍只有一个 writer。
实施时核验驱动实际 SQLite 版本包含
[WAL-reset 修复](https://www.sqlite.org/news.html)，而非只检查 npm 包名。

迁移 SQL 版本化并随代码入库；运行时独立迁移步骤在服务接流量前执行，不在
Next build 或每个请求中自动修改 schema。迁移前和每日使用
[SQLite backup API](https://www.sqlite.org/backup.html) 制作一致性备份，副本按权限
保存并有异机恢复方案；验证恢复与旧镜像兼容性。不能在 WAL 活跃时仅复制主 db，
也不能在应用回滚时自动用旧备份覆盖新注册账号。

**旧聊天处理（Owner 批准时更新）：** 网站尚未公开使用，不迁移旧 JSON。
保留忽略目录中的旧文件，新账号只读取 SQLite 中归属于自己的新会话；旧 UUID
与旧口令 cookie 不提供认领或访问权限。新用户读、写、重试和恢复同时验证 userId。

### 11.4 注册、登录与恢复流程

1. 用户在 `/register` 填邮箱、密码，昵称可选（认证层提供默认显示名）。密码策略见 ARCHITECTURE 的 Account and mail lifecycle，支持密码管理器
   粘贴，不强制符号拼凑；由框架做慢哈希。注册/重发/找回入口校验
   [Turnstile](https://developers.cloudflare.com/turnstile/plans/)（免费方案可用），
   叠加限流，而非把 CAPTCHA 当唯一额度保护。
2. 创建未验证账号和 credential 记录，发送 6 位随机 OTP，建议有效 10 分钟。
   注册提交不创建可使用 AI 的登录会话；失败/延迟可以在验证页手动重发。
3. 验证页单个验证码输入框支持整段粘贴/自动填充；60 秒重发间隔，建议同邮箱
   5 次/小时，单码最多 5 次校验失败。用途独立，旧码在重发时失效，成功码只用一次。
   限流在服务端持久化，刷新和重启不能重置。以上数值是实施建议，可配置。
4. 成功后设置 emailVerified，再通过邮箱＋密码登录。首版不依赖跨页面保留密码来
   自动登录；验证页提供返回登录入口。日常登录不发 OTP，未验证账号只走验证流程。
5. `/login` 支持登录、忘记密码、注册入口；框架 Route Handler 在
   `/api/auth/[...all]`；服务端每个私有路由取得 user/session，不能只检测 cookie 存在。
   Cookie 为 HttpOnly、生产 Secure、SameSite、host-only；退出撤销 session；
   忘记密码使用独立用途 OTP，重置后撤销其他登录会话。
6. 插件只用于邮箱验证和密码恢复，服务端禁用 OTP-only 登录端点并拒绝发送
   sign-in 用途短码，不留下“界面用密码、API 却能走其他入口”的旁路。
   显式设置 OTP 安全存储（插件默认可能是明文），建议使用服务端密钥化摘要；
   校验记录绑定规范化邮箱与用途，实现单次消费/并发重放回归。库 API 以锁定版本验证。
7. 注册/找回响应避免暴露邮箱是否已注册；登录失败统一提示。固定 baseURL/
   trustedOrigins 和站内 returnTo，验证来自可信 Tunnel 的客户端 IP；不信任任意
   x-forwarded-for。避免在日志/URL/localStorage 放密码、OTP 或会话 token。
8. 登录成功返回原阅读页；localStorage 草稿/会话选择按用户分区，退出与切换账号
   取消活动请求并清空可见私有历史。公开书籍和前端小工具仍可直接使用。

   同一能力，避免两个菜单的状态或退出行为不同。聊天关闭时仍可访问账号。
3. 新增账号专用只读身份接口与共享客户端状态，身份不依赖 AI 是否启用、
   模型配置、聊天初始化或额度查询。处理加载、匿名、失效、失败状态，失败
   时不把用户误认为已退出。响应 no-store，只输出页面所需的安全字段。
4. 登录支持站内 returnTo：从某个模块进入后返回该模块，直接从首页进入则
   返回首页；直接访问登录页无目标时也回首页。注册、验证、找回密码到重新
   登录之间保留返回意图；已登录用户访问登录/注册页提供安全返回入口。
   校验路径为允许的站内目标，拒绝外部 URL、协议相对地址及编码绕过，避免
   登录页循环。保留阅读页面可安全携带的查询参数，不在 URL 放凭证。
5. 全站及跨标签页统一更新账号状态；退出、登录、改名、失效后刷新相关界面。
   删除客户端可见的前一个用户数据，保留按用户隔离的草稿/偏好规则。

### 13.3 批次 B：账号中心最小完整版本

新增 /account，提供资料与安全两个清楚的区域，沿用现有组件、主题及中英翻译。

- 基本资料：显示邮箱、已验证状态、注册时间；允许修改昵称/显示名称（限长），
  邮箱此版本只读；自动首字母头像，不引入上传/对象存储。名字变更同步到全站。
- 修改密码：输入当前密码、新密码及确认；新密码沿用 8–128 字符、至少一个
  ASCII 字母和一个数字，允许符号，无大小写混合硬要求。成功后撤销其他会话，
  安全更新当前会话 Cookie；新旧密码和会话 token 均不进入响应正文、日志或浏览器存储。
- 登录设备/会话：显示由现有会话信息推断的浏览器/系统、登录时间、到期时间，
  标识当前会话，允许撤销单个其他会话及退出其他所有设备。它是“登录会话”，
  不是精确物理设备识别；不把 updatedAt 伪称为最后使用时间，不公开原始 token/IP。
  使用非凭证记录 ID 作为操作目标，服务端再校验属于当前用户。
- 保留找回密码及补验证邮箱入口；验证、重发及邮件异常均有明确恢复方式。
  会话不够新时提示正常重新登录；敏感账号变更验证当前密码，不放宽库的保护。
- 管理员入口仅对当前管理员显示；客户端不能提交或修改 role/status/verified 等字段。

Better Auth 库已有底层能力，但当前产品路由刻意不开放这些通用端点。实现时

  键盘事件报告时提示；不新增商业强度服务、外传密码或虚构“安全分数”。
- 区分错误密码、需重新登录、429、目标已撤销、服务失败、账号忙和停止未确认。
  已知停止未确认不得显示操作成功；网络超时/断线视为结果未知，先刷新账号/会话状态，
  再引导手动处理。密码是否更新不能从空响应或新昵称推断；必要时要求正常登录确认。
  安全写入不自动重试。限流只展示服务器已知的重试时间，没有就不编倒计时。
- 改密成功仍撤销其他会话并轮换当前 Cookie；保留账号级 AI 停止影响说明，并
  使用操作特定结果文案。昵称失败不提示密码错误，服务故障不写成“仍在配置中”。

**登录会话与恢复流程**

- 当前会话排在首位，显示有效会话数量及其他会话数量。单个撤销弹窗展示目标的
  推断浏览器/系统与登录时间；批量撤销明确范围与保留当前会话。相同浏览器会话的
  操作有可区分的 accessible name。不公开原始 UA、IP、token，不把 updatedAt 当活跃时间。
- 刷新时保留上次成功列表并说明正在更新；失败标明旧快照，过期身份不保留私有
  列表。确认撤销后更新列表；目标已经失效时刷新，不误报密码错误。
  被撤销按钮从 DOM 移除后，焦点回到仍存在的会话标题/刷新按钮；取消回原按钮。
- 验证邮箱和重置密码分别提供用途正确的发码重试。重置第二步提供“换邮箱/
  重新开始”，清掉旧 OTP/密码并重做挑战；网络发信失败保留邮箱及返回目标，
  明确发送受理不等于送达。保持注册/重置的通用账号存在性响应，不能暴露注册名单。
- 挑战组件显示加载、过期、失败及脚本无法加载状态，提供有限的显式重试。
  只有发送验证码的动作依赖有效 token，普通验证码提交继续按服务端规则判断。

**落点与依赖**：`src/components/auth/*`、`messages/en.json`/`zh.json`，必要时扩展
`src/lib/auth/*` 的安全错误映射。首批不需要新服务、凭证、数据库迁移或 paid AI QA。
错误字段/接口有变化时更新 ARCHITECTURE；登记模式后再改 DESIGN 对应实现。

### 14.5 批次 B：日常设置和只读概览

> 2026-10-14 已按本节范围本地实施，结果与偏差见 §14.10；本节正文仍是设计依据。

- **偏好设置**：提供主题（系统/明/暗）和语言（设备默认/中/英），明确哪些随账号

### 14.6 批次 C：更换邮箱与个人数据导出

> 2026-10-14：**C2 个人数据导出**已本地实施，结果见 §14.11；**C1 安全更换邮箱**已本地
> 实施并通过隔离数据与浏览器模拟验收，结果见 §14.12。两者都未发布，真实邮件送达仍待
> 单独验收。

**C1 更换邮箱**

1. 使用当前密码和 fresh session 确认操作，保留稳定 user.id、角色、资料、聊天归属
   及额度。旧邮箱授权、新邮箱验证均完成前，登录邮箱不变；旧邮箱无法访问时明确
   告知当前不支持自助更换，不能只凭新邮箱验证码绕过旧身份确认。
2. 使用更换邮箱专用的一次性目的记录，绑定用户、旧/新邮箱、事务 ID 和期限；
   不能复用注册/重置 OTP。提供待确认、重发、取消、过期状态。并发申请只保留明确
   的有效事务；最终数据库唯一约束处理争抢，重放/更换目标/错误验证码安全失败。
3. 验证失败或发信失败保持旧邮箱；最终提交才按现有生命周期停止 AI、原子切换
   邮箱并撤销登录会话，要求用新邮箱重新登录。未确认停止不得宣布改邮箱成功。
   给旧邮箱发送结果通知；提交后通知失败不应谎报“未改邮箱”或回滚已完成身份。
4. 对旧/新邮箱、IP、用户和全站发信预算做目的独立限制，保留找回密码预算。
   先用模拟收件箱覆盖失败和竞态；真实送达检查须单独指定收件人和发送数量。

官方 [用户管理文档](https://better-auth.com/docs/concepts/users-accounts) 说明库支持
更换邮箱及旧邮箱确认，但当前项目使用用途隔离 OTP，并禁用通用验证链接端点。
不能直接打开 change-email 当完整产品流程；实施前核对锁定的 Better Auth 1.7.7
能力与当前包装，先完成小型技术验证再确定具体协议。此处为适配判断，不声称已实现。

**C1 技术验证结果（2026-10-14，核对已安装的 better-auth 1.7.7 dist 源码）**

`email-otp` 插件确实带 `/email-otp/change-email`，但直接打开它不能满足本节要求：

1. 发送端点只认会话（`sensitiveSessionMiddleware` + 可选 `verifyCurrentEmail`），
   **不要求当前密码**，与第 1 条"密码 + fresh session 确认"不符。
2. `verifyCurrentEmail: true` 校验的是 `email-verification-otp-${旧邮箱}`，即
   **注册验证那条目的**的验证码；该码在注册验证成功时已被原子消费，已验证账号
   不再有可用值。这条路既做不到"旧邮箱无法访问时明确不支持自助"，又把
   注册目的和换邮目的混在一起，违反第 3 条不复用要求。
3. 标识符是 `change-email-otp-${旧}-${新}`，**没有事务标识**：无法表达待确认/
   取消/过期状态，无法在并发申请里指定唯一有效事务，重发也只是覆盖同一键。
4. 确认端点走 `internalAdapter.updateUser` 后 `setSessionCookie` **保留当前会话**，
   与第 6 条"撤销登录会话、要求用新邮箱重新登录"相反；而且它写 `user` 表，
   不触发我们挂在 `account` 表上的 `beforePasswordWrite` 钩子，等于**绕过账号级
   AI 停止栅栏**——这是 AGENTS 的硬约束。
5. 唯一性检查是先读后写的 TOCTOU，没有数据库约束兜底，不满足第 4 条竞态要求。
6. 新邮箱已被占用时它抛 `Email already in use`，会泄漏注册情况，违反第 8 条。
7. 发信走 `runInBackgroundOrAwait`，失败可能被后台吞掉，第 7 条要求发信失败
   明确保持旧邮箱。
8. 现状上该端点根本不可达：`options.mjs` 未配置 `changeEmail`（库会先报
   disabled），且 `handler.ts` 的 POST 白名单只放行 6 条路由，不含它。

因此 C1 采用**自建最小协议**：只用库做密码核验（`verifyPassword`）与既有会话/
哈希约定，事务状态由新增的 `email_changes` 表承载，提交阶段复用
`withAccountChange` + `beforePasswordWrite` 栅栏并在同一事务里改邮箱、撤销该用户
全部会话。正式接口与状态契约只记在 ARCHITECTURE §5"Email change"，UI 模式记在
DESIGN §5.13。

**C2 个人数据导出**

- 首版明确输出 JSON（带 schemaVersion、生成时间、计数）与便于阅读的 Markdown
  对话内容。包括自己的安全资料、对话/消息、状态、已有来源修订/上下文及已报告用量；
  不包含密码哈希、验证码、会话 token、其他用户、私有 env、SDK 内部文件或完整书籍缓存。
- 全程以服务器当前 user.id 和资源归属过滤，要求再次认证；浏览器下载不进入
  localStorage，响应私有且 no-store。导出不是公开分享链接。没有对话也能导出资料。
- 先统计规模；首版限制单次范围与内存，提供按对话/日期分段导出，并在输出中标明
  范围、截断和完整性。需要整库规模的完整账号导出时另设计受控后台任务、私有暂存
  和过期清理；不能无限读进内存，也不能把分段结果宣称为全量快照。
- 小范围在一致读取边界中导出；导出过程中账号变更/失效应终止后续访问。
  对生成中消息标明“截至导出时间”，不伪造完成状态。用双用户数据验证无交叉；
  导出前后账号、历史、用量和保留版本不变。不新增导入/跨账号合并能力。

### 14.7 后续候选与必须先决定的事项

- **二步验证**：2026-10-14 已完成锁定版本实测验证并按最小方案本地实施，契约见
  ARCHITECTURE §5“Two-factor authentication”，结果与未覆盖项见 §14.14。优先评估管理员
  需求；TOTP 的绑定确认、恢复码、忘记设备、禁用、登录与敏感操作挑战均已定义，并证明
  修改密码/找回密码不会绕过第二因素。Passkey 仍是后续独立范围，不与 TOTP 合并。
  验证记录如下。

  **对锁定的 better-auth 1.7.7 `twoFactor` 插件的实测（2026-10-14，用一次性数据库跑通
  完整流程，而非读文档推断）**：

  1. 插件的 schema 由 `getSchema`/`getMigrations` 直接生成，结论是**两处新增**：
     `user.twoFactorEnabled integer default 0`（可空、默认 0，因此老账号迁移后仍可登录）
     与 `twoFactor(id, secret, backupCodes, userId→user ON DELETE CASCADE, verified,
     failedVerificationCount, lockedUntil)` 加 secret/userId 两个索引。布尔值经适配器
     往返为真正的 JS boolean（实测 `twoFactorEnabled === false`），因此
     `verified !== false` 这类判断在 SQLite 上成立。
  2. `/two-factor/enable`（method 默认 totp）**不启用**：它写入
     `verified=0, twoFactorEnabled=0`，返回 `{method, totpURI, backupCodes}`；只有
     `/two-factor/verify-totp` 校验通过后才把两者翻真并轮换会话。这正好满足「完成首个
     TOTP 验证后才启用」，不需要自建事务表。
  3. secret 与恢复码在库里是**对称加密**（`storeBackupCodes` 默认 `"encrypted"`，密钥
     即 `BETTER_AUTH_SECRET`），明文只在 enable/regenerate 响应里出现一次。恢复码是一次
     性的：命中后从列表移除，并用「旧密文 compare-and-set」写回，并发双花返回 CONFLICT；
     重新生成整体替换列表，旧码立即失效。库另有 server-only `viewBackupCodes`，不暴露。
  4. 已启用后 `/sign-in/email` 的 after hook 会**先删掉凭据登录刚创建的会话**再返回
     `{twoFactorRedirect: true, twoFactorMethods: ["totp"]}`，并只下发签名的
     `better-auth.two_factor` 挑战 cookie；实测此时用该 cookie 调 `getSession` 得到
     `null`。因此「未完成挑战没有可用身份」是库自身保证的，不需要在每个读取点重复判断。
  5. 挑战有效期默认 600 秒，标识与尝试计数都存在 `verification` 表；5 次错误码会消耗
     挑战标识（必须重新登录），重放已消费的挑战返回
     `INVALID_TWO_FACTOR_COOKIE`。另有跨挑战、跨因素的账号级锁定：连续 10 次失败锁 15
     分钟（`accountLockout`，默认开启）。
  6. **已知的两个必须自行堵住的洞**：(a) `verifyTwoFactor` 优先使用已存在的会话，该分支
     的 `beginAttempt` 是空操作，即带会话调用 verify 端点不受尝试限流；(b) 两个 verify
     端点都接受客户端 `trustDevice`，一旦为真就签发 30 天免第二因素 Cookie。因此本方案
     不把任何 `/two-factor/*` 路径放进公开白名单，包装层自己构造载荷且永不传
     `trustDevice`，也不提供「信任此设备」。
  7. **找回密码不构成绕过**（实测源码）：`/email-otp/reset-password` 只返回
     `{success:true}`，不创建会话、不下发会话 Cookie，且
     `revokeSessionsOnPasswordReset: true` 会删除该用户全部会话；它也不改
     `twoFactorEnabled`，因此重置后的下一次登录仍会命中第 4 条的挑战。改密同理走
     `/change-password`，且 `revokeOtherSessions` 已有栅栏保护。
  8. 插件只注册 `/two-factor/` 前缀的 3 次/10 秒限流，且**不覆盖** `/sign-in/email`
     的挑战消耗；包装层需要自己的按账号/按 IP 尝试桶。**实施后才看清的直接后果**：这条
     3 次/10 秒的桶与「5 次错误码消耗挑战」共用同一个入口，因此密集提交时第 4 次起库直接
     返回 429，计数器不再前进，挑战要到第 8 次提交才真正关闭（实测见 §14.14）。若把 429
     当成「验证码错误」上报，用户会以为自己的验证器坏了并继续试，而真实的尝试预算也被隐藏。
     包装层因此把库的 429 原样映射为 `rate_limited`，挑战自己的 10 次/分钟桶再兜一层。
  9. 本方案不启用 `otpOptions.sendOTP`，因此第二因素只有 TOTP 与恢复码两种，不会为
     2FA 发任何邮件（`twoFactorMethods` 也只返回 `["totp"]`）。
- **Passkey**：2026-10-15 完成锁定版本实测并按最小方案本地实施，契约见
  ARCHITECTURE §5“Passkeys”，结果与未覆盖项见 §14.15。

  **对锁定的 `better-auth@1.7.7` 与 `@better-auth/passkey@1.7.7` 的实测（一次性数据库 +
  软件 authenticator 跑通完整流程，不读文档推断）**：

  1. **1.7.7 的主包不含 passkey**：`better-auth/dist` 与 `@better-auth/core/dist` 里
     `passkey` 只作为 `/passkey/verify-authentication` 出现在两个插件的路径匹配里，没有
     任何端点、schema 或 WebAuthn 校验实现。passkey 在同版本线已被拆成独立的第一方包
     `@better-auth/passkey`，其 peer 恰好要求 `better-auth@^1.7.7`、
     `@better-auth/core@^1.7.7`、`better-call@1.4.0`、`@better-auth/utils@0.4.2`——全部
     就是当前已装的版本。因此实施方式是**新增一个版本对齐的第一方包**，而不是升级认证栈；
     `package.json` 的 `overrides` 把 core/utils/better-call 钉在现有版本，防止 npm 因为
     peer 写的是 `^1.7.7` 而把 core 漂到 1.7.9（实测不加 overrides 时 `npm install` 直接
     ERESOLVE 失败）。新增运行时依赖只有 `@simplewebauthn/server`（校验）与其 browser 包，
     本仓库不导入 browser 包（见第 8 条）。
  2. **schema 纯新增**：`getMigrations()` 只产出一张 `passkey` 表（`name`、`publicKey`、
     `userId→user ON DELETE CASCADE`、`credentialID`、`counter`、`deviceType`、`backedUp`、
     `transports`、`createdAt`、`aaguid`）与 userId/credentialID 两个索引，`user` 不加列，
     unsafe changes 与 schema problems 均为空。
  3. **挑战是服务端一次性**的：`generate-*` 写入一条 `verification`（值里带
     expectedChallenge、type、userData），并把随机标识放进签名的
     `better-auth-passkey` Cookie；有效期硬编码 300 秒。实测注册响应重放与断言重放都返回
     `CHALLENGE_NOT_FOUND`，且注册/认证各自校验 `type`，两种用途不能互换。
  4. **origin 与 rpID 真被校验**：把 `origin` 与 `rpID` 作为插件选项钉成站点自己的值后，
     错 rpID、错 origin 的断言都返回 `AUTHENTICATION_FAILED`，不认识的凭证返回
     `PASSKEY_NOT_FOUND`；`expectedOrigin` 缺省时会取请求的 Origin 头，因此**必须由包装层
     钉死**，不能让调用方决定。
  5. **两处必须由产品自己堵住的洞**：(a) 两个 verify 端点都写死
     `requireUserVerification: false`，实测一个**没有 UV 标志的断言照样换到会话**；
     (b) `verify-authentication` 不受 twoFactor 插件的 after hook 覆盖（那个 hook 只匹配
     `/sign-in/email|username|phone-number`），实测 `twoFactorEnabled=1` 时 passkey 登录
     直接返回会话、不产生 `twoFactorRedirect`。
  6. **UV 可以在库里补上**：`registration/authentication.afterVerification` 都能拿到
     `verification.registrationInfo.userVerified` / `verification.authenticationInfo.userVerified`
     （simplewebauthn 13.3 暴露的真值），抛 `APIError` 会原样上抛且**发生在写库与建会话
     之前**——实测被拒的注册留下 0 行、被拒的登录不产生任何会话。注册侧再配
     `authenticatorSelection.userVerification: "required"`，让凭证从一开始就绑定 UV。
  7. **重复凭证**：库只在注册选项里下发 `excludeCredentials`，那是给浏览器的提示；实测同
     一把钥匙再注册一次会撞上 `008-passkey.sql` 追加的 `credentialID` 唯一索引并返回 500。
     包装层因此先按 `response.id` 查一次给出明确答复，唯一索引仍是真正的保证。
  8. **不引入客户端认证栈**：`@better-auth/passkey/client` 依赖
     `createAuthClient`/nanostores/`@simplewebauthn/browser`，而本仓库前端从来只用 `fetch`
     调自己的包装路由；为 passkey 单独引入一套客户端会扩大栈面，也绕开包装层的字段白名单。
     因此 UI 直接调用 `navigator.credentials.create()/get()`，只做 base64url 与 ArrayBuffer
     的转换。
  9. **列表端点会返回 `publicKey`/`credentialID`/`aaguid`**：这些不是秘密，但产品界面不需要，
     包装层只投影 id、名称、来源标签、时间与同步性。

- **安全活动**：✅ 2026-10-14 已按最小方案本地实施，结果见 §14.13。现有登录会话不等于
  完整安全日志；新增的是少量脱敏的**已确认**成功事件（改密/改邮箱/撤销，且区分单个与
  批量），字段与保留时限先定契约，不展示精确定位/IP，不记录密码，也不从现有会话倒推
  历史。新设备通知会增加邮件消耗和误判，仍独立于本记录，未实施。
- **注销**：2026-10-15 已按最小方案本地实施，**逐项删除清单见 ARCHITECTURE §5“Account
  deletion”**（那是该清单的唯一归属），界面模式见 DESIGN §5.17，实施结果与未覆盖项见
  §14.16。前提已核对：个人数据导出（§14.11）可用，且 `conversations`/`ai_usage` 的外键
  **确实没有**用户级联删除，因此库自带的 `deleteUser` 不构成安全删除方案——删除必须按
  子表先行的顺序在一个事务里完成，`foreign_keys=ON` 就是漏项的守门人。已定下的关键决定：
  (1) **不存在「稍后自动删除」**——冷静期只解锁第二次确认，最终一步必须由本人重新完成
  密码 + 实时因素 + 输入自己邮箱的仪式，逾期未完成即**失效回原状**，因此没有后台任务、
  没有 cron，也不会有无人观察的静默删除；(2) 导出是**前置条件**而非建议，且必须在申请之后
  重新生成一次；(3) 唯一满足 `/admin` 谓词的账号**不能自助注销**，因为提权只有 CLI 路径、
  没有降权路径；(4) 邮件元数据**匿名化而不是删除**，以免站点自己的每日预算统计失真；共享
  书籍版本、其他用户数据与既有备份一律不动，本功能**永不裁剪备份**；(5) 防复活靠数据库旁边
  那份 append-only 意图文件 + `migrate()` 时的对账（按永不复用的 user id 匹配，因此同一邮箱
  重新注册不受影响），而它的边界——整卷回滚仍可带回身份、离线备份完全在机制之外——写进
  ARCHITECTURE 而不是含糊带过。
  **执行边界**：本批只在一次性 fixture 里删除过数据；对任何真实 retained 数据执行删除，
  需要 owner 就上面那份清单另行、明确地批准。
- **外部能力**：第三方登录要先证明安全账号绑定与恢复，头像上传要有文件验证和
  存储预算，跨域 SSO 要另定 cookie/域边界；当前没有充分理由为这些增加服务。

这些是后续产品决策，不把合规、计费、头像和完整管理员后台强塞进账号中心。

### 14.11 C2 个人数据导出本地实施结果（2026-10-14）

C1 更换邮箱与 D 仍未获准。契约正式文本在 ARCHITECTURE §5“Personal data export”

  不要密码、不持账号变更栅栏、不改动任何数据。

- 响应 `no-store` + `vary: Cookie` + `Content-Disposition: attachment`，文件名只含日期；
  界面用同源 `<a download>` 直接下载，因此导出内容不进入 localStorage/sessionStorage、
  不进 URL、不构成可分享链接。没有导入、跨账号合并或导出即删除能力。

### 14.12 C1 安全更换邮箱本地实施结果（2026-10-14）

§14.6 的 C1 部分已按上面「自建最小协议」的结论实施，**未合并、未部署、未向任何
真实邮箱发信**；D 仍未获准。接口与状态契约的正式文本在 ARCHITECTURE §5“Email
change”，UI 模式在 DESIGN §5.13，这里只记取舍与边界。

- 提案里「旧邮箱授权 + 新邮箱验证」被实现为**两个独立验证码**：`start` 给当前地址
  发 `change-email-old`，给目标地址发 `change-email-new`，各自存摘要与各自的五次
  尝试预算。`verify` 一次提交两个码，任一槽位不匹配都不改动邮箱，因此「只拿到新
  邮箱的码」在协议上就无法绕过旧地址确认，而不只是文案上劝阻。
- 库端点确实不满足 §14.6 列出的 8 条，因此没有打开它：`/api/auth` 白名单不变，
  `options.mjs` 仍不配置 `changeEmail`。只借用库的 `verifyPassword` 与既有
  会话/哈希约定；事务状态全部落在新的 `email_changes` 表。
- 提交只在 `withAccountChange` 栅栏内发生，且必须先 `beforePasswordWrite()` 确认
  AI 终态；未确认停止返回 409 并把事务重新打开供重试，邮箱与会话都不变。确认后
  一个 immediate 事务同时改 `user.email`/`emailVerified`/`updatedAt` 并删除该用户
  全部会话，`user.id` 不变所以历史、用量、偏好与保留来源版本都不迁移。
- 「新地址已被占用」不在发起时回答，只在提交时以 `email_taken` 失败：发起与不发起
  的响应完全一致，界面据此回到空闲态并给出中性说明，避免变成注册探测 oracle。
- 提交后的旧邮箱通知失败只报告 `notified: false`，绝不把已生效的变更说成未完成，
  也不自动重发。
- 实施中修掉三处只在真实浏览器里才暴露的问题（详见 GOTCHAS 与 DESIGN §5.13）：
  共享 Turnstile 组件在折叠卡片内因 `lazy` 脚本策略永远停在“加载中”；待确认面板
  原先没有验证码组件，导致重发必然 403；窄屏下触发器里的掩码地址徽标与标签重叠。
  同时把客户端重发冷却对齐服务器每分钟一发的桶（30s→60s）。
- 未覆盖：真实邮件送达（本消息未授权）、真实手机浏览器验收、付费 AI 请求进行中时
  的停止时序（用本地活动查询桩验证，见 HANDOVER §7）。

### 14.13 安全活动记录本地实施结果（2026-10-14）

  「账号从没变过」。
- 改密会连带撤销其他会话，但它是**一个操作、一条记录**；库在那一步还会轮换当前会话行，
  所以更不该把这次连带写成第二条「撤销」事件。
- 批量撤销先数清实际受影响的会话数，为 0 时**完全不记账**，因此重复点击或held Enter
  不会凭空多出一条「已退出 0 个会话」；单个撤销目标已不存在时上游就返回 404，同样不记。
- 换邮箱的事件写在**同一个 immediate 事务内**：写不进记录，邮箱也不会改，二者不可能
  不一致。改密与撤销由库拥有其事务，只能在确认响应后补记；此时若补记失败则**吞掉而不
  报错**——把已经成功的密码修改说成失败会诱导用户重试一个已经不可能成功的操作。这条
  不对称是刻意的：记录在已确认变更之后尽力而为，在变更之前绝不尽力而为。
- 只存操作类型、时间、以及会话列表已经在用的那两个推断标签（浏览器/系统）。不存密码、
  验证码、Cookie、会话 token、原始 UA、IP、位置、完整新邮箱地址或任何模型/聊天内容；
  换邮箱只存掩码后的目标地址。
- 读取只有一个 `GET /api/account/activity`，与撤销会话、导出同一档 24 小时新鲜度门槛
  （它属于安全数据，不是普通页面读取），SQL 只按调用者自身 `user.id` 过滤，不接受任何
  缩小或放大范围的参数；本批**不做管理员视图**，管理员身份继续只来自服务端 `role`。
- 保留 180 天且每账号最多 100 条，超期与超限的清理只发生在写入时、只针对本表；账号、
  会话、聊天、书籍版本与备份都不在清理范围内，DEPLOYMENT §12 的通用保留/裁剪决策仍是
  独立且未获准的事项。

### 14.14 TOTP 二步验证本地实施结果（2026-10-14）

§14.7 的「二步验证」已按最小方案本地实施，**未合并、未部署、未为任何真实账号开启，
也未发送任何真实邮件**。范围只有 TOTP 与恢复码：不启用 `otpOptions.sendOTP`（因此
不会为 2FA 发信），不做 Passkey，不做「信任此设备」。认证契约在 ARCHITECTURE §5
“Two-factor authentication”，界面模式在 DESIGN §5.14，这里只记取舍与实际结果。

- 全部结论建立在**锁定的 1.7.7 实际 dist 与一次性数据库跑通的流程**上（§14.7 的 9 条
  实测），不引用其他版本文档。
- 契约的核心是一条不变式：**只要会话是在账号已启用二步验证的情况下建立的，它就一定
  经过第二因素**。库自身保证前向（凭据登录刚建的会话在挑战签发前就被删掉），唯一的历史
  缺口是启用之前就已存在的会话；因此**绑定完成时撤销该账号全部会话**，包括当前这一个，
  不变式从打开的那一刻起成立。也正因为有这条不变式，身份解析层不必在每次读取时重复
  检查因素。
- 绑定是两步，**第一步什么都不启用**：`enable` 需要新鲜会话与当前密码，只写入未验证的
  secret 与一批恢复码；`confirm` 需要一个来自新设备的有效码才翻真并撤销全部会话。放弃
  中间步骤既不会锁死账号也不会削弱它，界面在此期间必须写「尚未开启」。
- 关闭与重新生成恢复码除密码外还**必须证明当前因素**（六位码或一个未用恢复码，按形状
  区分）。否则拿到密码和被盗 Cookie 的人可以静默摘掉第二因素。重新生成整体替换列表，
  旧码当场失效。
- **挑战面只接受一个 `code` 字段**，其余键（含 `trustDevice`、`disableSession`）一律
  400，因此这两个库选项在结构上无法从浏览器到达；`/two-factor/*` 全部留在公开白名单
  之外，包装层是唯一的第二因素入口。库在「已有会话」分支不对尝试计数，所以挑战只允许
  由**没有会话**的调用者回答，否则返回 `signed_in`。
- **尝试限流的真实边界与文档不同**：库对 `/two-factor/` 另有 3 次/10 秒的总限流，密集
  提交时它会先命中并让挑战的尝试计数器停住，实测关闭发生在第 8 次而不是第 5 次。包装层
  把库的 429 原样报成 `rate_limited`（而不是「验证码错误」），否则用户会以为自己的验证器
  坏了并继续猜，真正的预算也被掩盖；挑战自身与 IP 各 10 次/分钟的桶再兜一层。契约文字以
  实测为准（ARCHITECTURE §5）。
- 忘记设备与恢复码全部丢失**没有自助路径**，也没有人工后门、自动降级或把挑战结果交给
  客户端声明；这是本功能唯一不可逆的后果，因此在绑定完成前就写明白，而不是事后。恢复
  账号需要一个单独设计与批准的离线流程，本批不含。
- `007-two-factor.sql` 由插件自身生成、纯新增（`user.twoFactorEnabled` 默认 0 加
  `twoFactor` 表与两个索引），因此老账号迁移后照常登录，回滚只需退回旧镜像且不恢复任何
  数据；不存在把已有账号变成无法登录的路径。
- 两处库行为会伤及既有产品契约，已在包装层处理并记入 ARCHITECTURE：挑战通过后由库自己
  创建的会话**不带请求上下文**，若不回填 UA，登录会话列表与安全活动记录里每次二步验证
  登录都会显示「未知设备」；secret 与恢复码以 `BETTER_AUTH_SECRET` 对称加密，**轮换该
  密钥会让已启用二步验证的账号无法再完成登录**，故该变量从「可重生成」升格为必须长期
  稳定的密钥材料。
- 安全活动记录沿用 §14.13 的机制，只新增三种**已确认**结果：开启、关闭、替换恢复码；
  不记录任何因素秘密，也不把「用恢复码登录成功」当成历史安全事件（那是一次登录，不是一次
  变更）。
- **未覆盖项**：真实手机与真实验证器应用的验收没有做。本批所有码值都是在浏览器里按
  RFC 6238 从界面显示的那串 base32 设置密钥独立算出的（先 base32 解码，再以解出的字节做
  HMAC-SHA1 密钥，与库的口径一致），因此证明了「界面给的密钥能算出库接受的码」，但没有
  在物理手机上用某个具体 App 扫过/输过。密码管理器与浏览器对 `one-time-code` 自动填充的
  真实行为、手机键盘/IME、以及为生产 owner 账号开启二步验证，都仍待 owner 在真机上验收。

### 14.15 Passkey 本地实施结果（2026-10-15）

§14.7 的「Passkey」已按最小方案本地实施，**未合并、未部署、未注册任何生产凭证，也没有
域名变更、真实邮件或付费调用**。范围只是「已有账号的一种额外登录方式」：不做 passkey
优先注册、不信任 attestation（`fmt: "none"` 一律接受，AAGUID 只用于标签、永不白名单）、
不做管理员视图、不做浏览器 conditional/autofill 中介。认证契约在 ARCHITECTURE §5
“Passkeys”，界面模式在 DESIGN §5.16，这里只记取舍与实际结果。

- 依赖变化的实际面只有一个版本对齐的第一方包：`package-lock.json` 是 **314 行新增、0 行
  删除**，没有任何既有包换版本（新增的是 `@better-auth/passkey@1.7.7` 与其自带的
  `@simplewebauthn/server@13.3.3`）。`overrides` 是为守住这个结论而加的，不是升级手段。
  客户端不引入任何认证库，UI 直接调 `navigator.credentials`。
- 组合规则被写成一条可测的不变式：**每个会话都由「密码 + 第二因素」或「已用户验证的
  passkey 断言」之一建立**。已验证的 passkey 满足第二因素，但**不取代密码**：改密、提交
  改邮箱、关闭二步验证、重新生成恢复码仍要当前密码，要求实时因素的地方仍要 TOTP 或恢复码，
  passkey 不能顶替；反过来开启二步验证后，注册/移除 passkey 除密码外还要实时因素，否则
  「拿到密码和 Cookie 的人可以自行加装一把后门钥匙」。库自身两处都不保证这些（不要求 UV、
  passkey 登录不进 2FA after hook），已在 `afterVerification` 里补上，且实测被拒的仪式
  不留任何行、不发任何会话。
- **WebAuthn 的 user handle 是每次仪式随机生成的**（插件源码
  `generateRandomString(32)`），账号绑定只存在于服务端 challenge 行的 `userData.id` 与
  验证后的 `userId` 比对。因此 authenticator 里那个 handle 不含可跨账号关联的稳定标识，
  满足「不增加隐式跨账号绑定」；代价是 resident key 的 handle 对服务端没有意义，登录必须
  按 credentialID 回查，`user.id` 也**不能**当作跨设备线索。
- schema 与回滚：`008-passkey.sql` 由插件 `getMigrations()` 生成、纯新增（`user` 不加列），
  另加一条 `credentialID` 唯一索引作为插件之外的硬保证；`006-security-events.sql` 的
  `kind` CHECK 就地加两个值（该迁移尚未在任何环境部署过，因此不需要新的 alter 迁移）。
  回滚等于退回旧镜像，不恢复任何数据；已有账号既不受影响也不会因此无法登录。
- **一个只有真浏览器才能暴露的缺陷**：账号已有第一把 passkey 后，第二把注册必然失败，
  而服务器端为同一账号连发 10 把不同凭证都成功。原因是服务端下发的
  `excludeCredentials[].transports` 是**数组**，客户端却对它 `.split(",")`，`TypeError`
  发生在构造选项时、提示框出现前，被仪式包装器归成通用「失败」。已按实测形状修正，并把
  该形状钉成 `tests/passkey.test.cjs` 里对 `register/start` 响应的断言——这条路径只存在于
  浏览器，服务端测试是唯一能看见它的地方（GOTCHAS 记了同一条）。
- 服务端回归 17 条（`tests/passkey.test.cjs` + 自建软件 authenticator `tests/webauthn-fixture.cjs`，
  不引入 `@simplewebauthn` 的测试依赖）覆盖：两步注册与密码栅栏、无 UV 被拒且不留痕、
  挑战一次性与用途绑定、错 rpID/错 origin/未知凭证、重复凭证、数量上限、库路径在公开门
  外全部 404、登录面只接受凭证、已登录浏览器不能再答登录挑战、凭证按账号隔离、重命名、
  移除后密码仍可用且只记一条事件、与二步验证的组合两条、列表需要近期登录、以及「任何
  秘密都不被存储或回显」。
- 浏览器验收用**一次性 headless Chrome + CDP 虚拟 authenticator**（独立临时 profile、独立
  调试端口、跑完即删，只连回环 fixture）。实测：注册→列表出现行→改名→移除→安全活动两条
  事件→用 passkey 单独登录成功；12 组 locale × theme × 宽度（360/768/1280）在**两行凭证**
  状态下逐组断言实际生效的 theme class 与 `document.documentElement.lang`，卡片与登录页均
  无横向溢出、无被裁切文本；axe-core（wcag2a/aa/2.1a/2.1aa）对 passkeys 卡片与登录主区各
  **0 violations**；键盘顺序为触发器→每行重命名/移除→密码→显示密码→名称→添加，9 个控件
  都有可见 focus ring；24 组导航之后再用 passkey 登录仍然成功。
- **列表要两行必须换一台虚拟 authenticator**：同一台设备对同一账号+RP 的第二把凭证会按
  exclude 提示直接拒绝，这正是 Windows Hello / Touch ID 的真实行为，因此「第二把 passkey」
  在产品语义上等于「第二台设备」。此时界面显示的是浏览器给出的失败文案，而服务端的
  `already_registered` 只在浏览器真的把响应发上来时才会命中——WebAuthn 对这种情况没有
  独立错误名，包装层只能把它归到「取消/失败」一档。是否要为它另写文案，是一次 copy 决定，
  不影响安全边界。
- **未覆盖项**：真实手机、真实同步 passkey 与硬件安全密钥的验收都没有做；虚拟 authenticator
  证明的是浏览器↔服务端链路，不是跨设备。生产域名（`utils.lzhdev.com`）下的 rpID/origin
  行为未测——本仓库的 fixture 只能用 `localhost`，因为浏览器拒绝把 IP 地址当 rpID（这条
  限制写进了 ARCHITECTURE §5）。密码管理器托管的 passkey、Windows Hello 实际提示流程、
  iOS/Android 键盘与生物识别回退、以及「同一浏览器多账号」的真实选择器体验都未验证。
  passkey 不改变 §14.14 的恢复故事：忘记设备仍只有 owner 自己掌握的密码与恢复码这条路，
  本批没有、也不应新增任何人工后门。

### 14.16 账号注销本地实施结果（2026-10-15）

§14.7 的「注销」已按最小方案本地实施，**未合并、未部署，并且从未对任何真实账号或任何
retained 数据执行过删除**——本批删掉的全部是一次性 fixture 里由测试脚本自己创建的账号。
逐项清单本身在 ARCHITECTURE §5“Account deletion”，界面模式在 DESIGN §5.17，这里只记取舍
与实际结果。

- 设计的地基是两条实测事实，不是推测：`conversations.owner_user_id` 和 `ai_usage.user_id`
  只有 `REFERENCES user(id)` 而**没有** `ON DELETE CASCADE`，因此在 `foreign_keys=ON` 下裸删
  `user` 会直接失败；其余产品表都带级联。于是删除顺序是「先子后父、单事务」，而**漏掉任何
  一张表都会让最后那句 `DELETE FROM user` 抛错并整体回滚**——数据库自己的外键就是防漏项的
  守门人，测试再用 `PRAGMA foreign_key_check` 复核一遍。
- 状态机刻意做成**不需要后台任务**：`pending` 的资格与失效都由时间戳在读时算出，逾期未确认
  就回到「无申请」。这是「不要模糊的稍后删除」的直接后果——站点里不存在一个会在无人观察时
  把账号删掉的计时器，最终一步必须由本人再走一次完整确认。
- 两个期限给的是产品依据而非合规依据，并写进 ARCHITECTURE：冷静期 7 天，够长到让被盗会话
  发起的删除在正常回访中被发现且可无损撤回，也短于 14 天的会话寿命，因此一个申请不会由早已
  过期的登录来支配；可确认窗口 30 天，逾期即失效，避免「待删除」状态无限堆积。
- 导出默认是**前置条件**：申请之后生成过「完整账号」导出才正常放行，按单个会话或按日期范围
  的导出不冒充完整副本。**2026-10-15 审核修复时 owner 明确选择的例外**：当无法保存完整
  副本（例如超过单次导出上限），本人可在最终确认框中单独确认「尚未保存完整副本，仍要删除」。
  服务端仅接受最终请求中的布尔值 `skipExport: true`，不伪造导出时间，也不跳过密码、实时
  因素、冷静期、邮箱确认或最后管理员保护。服务端只能知道「生成过」，不能知道是否保存到磁盘。
- 最后一个管理员的判定直接复用 `/admin` 自己的谓词（`role='admin' AND status='active' AND
  emailVerified=1`），因为提权只有 CLI 一条路、代码里根本没有降权路径；申请和最终确认两处都
  查，浏览器侧不可绕过。
- 防复活的记录刻意放在数据库**外面**：`deleted-accounts.jsonl`（与库同目录、append-only、
  mode 600、不在任何 SQLite 备份里），由 `migrate()` 在开始服务前对账——这也是它被写进
  `migrate()` 而不是运行时某个懒加载点的原因：生产入口、`npm run db:migrate` 和每个测试
  fixture 都已经跑过这一步。匹配键是永不复用的 user id，因此同一个人日后用同一邮箱重新注册
  （新 id）不会被误删。诚实的边界也写进文档：整卷回滚会连这份文件一起回退，owner 自持的
  离线备份完全在机制之外。
- 意图行在 immediate 事务内、最后管理员检查之后、数据删除之前写入并 `fsync`。崩溃恰好夹在
  意图与提交之间时，库里没有 tombstone、账号仍在，
  对账会把这条「未完成的授权」做完——因为能让这行存在的唯一前提，是本人已经走完密码 + 实时
  因素 + 输入自己邮箱 + 已过冷静期 + 已有完整导出或明确放弃副本这一整套确认。
- 邮件元数据是**匿名化而不是删除**：`email_hash` 换成固定标记，`purpose`/时间/状态/provider
  id 保留，这样站点自己的每日邮件预算仍统计它实际发过的信；反过来 `verification` 里那行
  **明文邮箱**标识符必须删干净，否则地址会在账号消失后继续活着。IP 维度的限流桶不可归属到
  某个账号，保留。
- 活动 AI 的停止复用既有栅栏（`withAccountChange` + `beforePasswordWrite`）：30 秒内确认不到
  取消就返回 `stop_unconfirmed`，此时**不删任何东西，也不声称删了**；同一账号上并发的安全变更
  直接 `account_busy`，栅栏期间更早认证的请求也无法再登记（账号版本号已推进）。
- 客户端清理只针对被删账号自己的 `htlb_chat_*:<id>` 键与 `sessionStorage` 里那封待验证邮箱；
  设备主题键描述的是浏览器而不是账号，故意保留。为此把散落在三处的存储键名收进
  `src/lib/chat/keys.ts` 一处定义——「清理用的是另一套字符串」正是这类功能最安静的失败方式。
- 回归 18 条（`tests/deletion.test.cjs`）覆盖：迁移纯新增且旧账号不受影响；申请不动任何数据、
  不留安全事件、重复申请 409；密码与实时因素两道门槛；冷静期与导出两个前置（含「窄范围导出不算」）；
